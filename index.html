Agent Skills 分享路线

先扫一眼今天的安排。开头聊 Matt Pocock 的仓库，里面有 27 个正式 skill，串起了一条从聊想法到落地的开发主线。东西不少，我挑大家平时问得最多的几个展开讲，像 grill 系列、ask-matt、wayfinder、prototype，还有用来复盘的 retro。

接着看 pstack。它跟 Matt 的画风不太一样，平时你基本只需要记一个总入口 poteto-mode。待会儿我会经常提到 playbook 这个词，你可以把它理解成一份写死了步骤的 SOP 清单，比如修 bug 该先查什么、再验什么，照着一步步推进。再往后的 plannotator 管的是另一头：它在本地起一个浏览器审阅界面，专门管看 plan、看 diff 和写批注这事。

有意思的是，这三位作者脾气不太一样，观念甚至有点打架：Matt 讲究动代码之前先让 agent 把你问透；pstack 作者挺反感写长篇大论的 plan，觉得最好的 spec 就是直接写出来的代码；plannotator 则默认你在 agent 开工前得先把 plan 审一遍。记住这三个思路，后面听起来会清楚很多。

Agent Skills 分享概念

正式开讲前，咱们先把一个概念对齐，后面满屏都是它：skill 其实分两种触发方式。

一类叫 user-invoked，说白了就是你不喊它，它绝不动。它的 frontmatter 里标了 disable-model-invocation: true，只有你自己敲斜杠命令才会跑，平时干的是搭流程架子的活。另一类叫 model-invoked，你手敲也行，agent 读到 description 里的 “Use when…” 觉得手头的活正好对上号，也会自己加载进来。这类 skill 里装的都是具体能复用的做法，比如怎么盘问需求、怎么写单测。

你看右边贴出来的，就是 grill-me 的全部源码——真没省略，正文就一行：去调用 grilling。grill-me 自己只是一个很薄的入口壳子，真正干活的套路全写在被它调起来的 grilling 里。Matt 整套仓库都是这种分层思路：入口管流程，底层 skill 管手艺。而且他定了个规矩，入口 skill 可以调底层 skill，但入口之间不能互相套娃。

相比之下，pstack 走的是另一路：几乎清一色全是手动触发。也就是说你装完 pstack，只要不敲命令，它对你的 agent 零干扰；真要用的时候，要么你自己指名道姓敲出来，要么丢给 poteto-mode 帮着分流。

先从 Matt Pocock 的 skills 仓库说起。这个仓库起名挺直白，叫 Skills For Real Engineers，他在简介里写得很清楚：这是他每天干正经工程活攒下来的 skill，不走 vibe coding 那套随手糊代码的路子。

他为什么单开一套呢？像 GSD、BMAD、Spec-Kit 这些大框架，习惯把整个研发流程全接管过去。听起来省心，真用起来你会发现控制权没了，万一框架自己的流程卡壳或者出 bug，你连从哪下手改都不知道。所以 Matt 反着来，把每个 skill 做得很轻，你能看懂、能按需改，想单用哪个或者怎么拼全看你自己。

当前版本是 v1.3.2，一共 27 个正式发布的 skill，MIT 协议。Claude Code、Codex、Copilot、Gemini CLI 这些主流工具都原生支持，其它 agent 也可以通过 skills.sh 装进去。

Matt 在 README 里专门写了一段 “Why These Skills Exist”，挑出来的正是咱们平时用 agent 写代码最头疼的四个翻车现场，每个坑他都配了对口的工具。

最让人抓狂的肯定是左上角这个：聊了半天你以为它全懂了，代码一跑发现根本没按你的想法走。他的解法挺狠——干活前先别让它写代码，反过来让它用 grilling 把你拷问一遍，直到把所有模糊的角落都抠清楚。Matt 自己说这是仓库里最受欢迎的 skill，几乎每次改代码前都值得来一轮。

聊需求的时候还能一起治另一个毛病：agent 说话特别啰嗦。多半是因为它不认得你们团队的业务黑话，只好绕一大圈去解释一个概念。grill-with-docs 会边追问边帮你在项目里攒一份 GLOSSARY.md 词汇表；碰到几句话说不清的架构取舍，还会记成一段 ADR——也就是架构决策记录，写清楚当初怎么定的、为啥这么定。

等真开始写代码了，最怕的是没有反馈回路，agent 纯靠猜，写出来的东西压根跑不起来。所以得给它套上类型检查、浏览器和自动测试。日常开发走 tdd，用红绿循环——先写个会报错的失败测试，再补代码让它变绿，每次只推进一小步；碰到邪门的难 bug，就用 diagnosing-bugs，先想办法造出一个能稳定复现、稳稳报红的测试，再动手修。

最后一个坑很多人感同身受：agent 产代码飞快，结果过两周一看，项目已经糊成一团泥球了。这里对应的是 improve-codebase-architecture 和 to-spec。Matt 建议隔三差五跑一次体检，专门揪那些接口铺得老大、里面没干多少正事的“浅模块”，把它们往“深”了重构——对外接口收窄，复杂度藏在里面。不过他自己也打了预防针，这玩意儿是日常保养，真等代码库已经烂透了再指望它来救火，它也理不顺。

平时从零做一个功能，走中间这条主线就行：先用 grill-with-docs 把需求和边界问透；聊着聊着要是发现某些交互或方案光靠嘴聊真定不下来，就绕个弯做个 prototype 试一下水；敲定之后用 to-spec 写成正式 spec，to-tickets 拆成带依赖关系的任务单；接着 implement 一张张票往下干，它内部会自己带上 tdd 和 code-review；活干完别忘了跑个 retro，把这次踩到的坑补回仓库配置里。

接着聊大家最常听到的 grill 系列。刚翻这个仓库时，很多人会被三个长得很像的名字绕晕：grill-me、grill-with-docs，还有个 grilling，看着像三套工具，其实点开源码看一眼就秒懂。

真正干活的是右上角的 grilling，整套追问方法全写在它里面。左边那两个纯粹是给人敲命令的薄壳——grill-me 正文就一句话，直接调 grilling；grill-with-docs 也一样简洁，就多挂了一个 domain-modeling。

所以你不管敲哪个，agent 盘问你的套路完全一样。唯一的区别就在 domain-modeling 这一层：它会在聊天过程中盯着你的用词不放，一边对照现有代码，把新定下来的概念当场记进 GLOSSARY.md，碰上关键取舍还会提议补一篇 ADR。

平时选起来也没啥好纠结的：只要在代码仓库里准备改东西，默认用 grill-with-docs；手里压根没 repo，比如就想理清一个方案或者准备一场分享，那就用 grill-me，干干净净不碰文件。另外，triage、wayfinder 还有 improve-codebase-architecture 底层也都复用 grilling，习惯了它的提问节奏，后面好几个 skill 上手就快多了。

Design tree

一个决定定下来，会引出依赖它的下一批问题。

一轮问完整个 frontier

现在条件够问的，一轮全抛出来；依赖本轮答案的留到下一轮。

每题带推荐答案

特意写成回 “yes” 就等于采纳，你只管纠正不同意的。

事实它查，决定你做

代码里能查到的绝不问你，丢给 subagent 并行查，不耽误聊天。

结束条件

问题全清空、且你点头确认共识之前，绝不提前动手。

mattpocock/skills“Finding facts is your job, never the user's.”

大家平时让 AI 问需求，经常被问得挺烦——要么一次甩来十几道题根本答不过来，要么挤牙膏一样一次只问一句，聊半天还在原地打转。grilling 在提问节奏上设计得很讲究，你看左边这段模拟对话。

它在脑子里会把需求拆成一棵决策树。每一轮，凡是前置条件已经明确、眼下就能定下来的问题，它会打包成一批一次全问出来，叫 frontier；至于那些得看你这轮怎么答才冒出来的新分叉，先憋着留到下一轮。就像左边我刚回完 Q2 说要导出全量数据、还得走后台任务，它下一轮立刻顺着这个分支追问：那后台跑完了怎么通知用户？

用起来最省心的一点是，每道题都带着编号和推荐答案，而且特意写成你直接回个 yes 就等于采纳。实战里八成问题扫一眼觉得靠谱，敲个 Q1 yes 就过了，真要打字解释的只有你不同意的那一两条，省了不少口舌。

还有一条分工规矩特别戳工程师痛点，就是页脚这句英文原话：“Finding facts is your job, never the user's.” 只要是看代码、翻配置就能查明白的事实，它直接派个 subagent 后台去翻代码，懒得跑来问你“你们现在用什么消息队列”，也不耽误继续跟你聊别的问题。真正涉及业务取舍的决定才交给你拍板。直到树上所有分叉都问清、而且你明确点头说达成共识了，它才会收手。

前面讲的 grill-with-docs 适合一个 session 就能聊透的需求。但干活时难免碰到另一种场面：接了个全新项目，或者一个特别庞大的 feature，大到单次对话根本装不下，甚至从哪下手都还在雾里。这时候就轮到 wayfinder 出场了。

它的思路挺像探险画地图，而且就画在你的 issue tracker 上。它会建一个带 wayfinder:map 标签的主 issue，固定分五个区块：要去哪、备注、已经定下来的决定、还没聊清楚的盲区，以及明确不做的范围。接着把眼前最急着解决的问题拆成子 issue 挂在下面，每张子票只盯一个问题，叫做 decision ticket。

这些子票按解决方式分了四种：research 专查仓库外面的文档和资料，丢给 subagent 后台并行跑，不用人盯着；光靠聊拿不准的交互或布局，标成 prototype 跑个小 demo 试一下；最常见也默认用的是 grilling，拉着你按前面那套方法一轮轮盘清楚；至于像提前找人开测试账号这种前置手工活，就归到 task 里。

用起来分两种姿势。第一次丢个模糊想法进去，它只负责把地图搭起来、建好首批子票、把能自动查的 research 并行跑掉，然后就停。后面每次带着这张 map 回来，它就挑一张子票认领、解决、把结论写回主地图再关票。而且它立了条硬规矩：除了 research，一个 session 最多只解一张票，保证每个关键决定都是在干净的上下文里做的。

最后补两句提醒：wayfinder 只管把迷雾里的决定一个个敲定，自己不动手做正式交付；也别拿大炮打蚊子，ask-matt 里都明说它更慢、更重，要是需求边界本来就清楚、一个 session 聊得完，直接走 grill-with-docs 省事得多。等不管哪条路把前期问题都摸透了，接下来就要正式把决定写成 spec，一路推到代码实现。

不管前期是用 grill 还是 wayfinder 把需求盘清楚、仓库脉络也理顺之后，就进了主流程的后半段：写 spec、拆票、开工。

先敲 to-spec。这时候它不再继续追问，把刚才敲定的内容收拢成一份完整的 spec，发到 issue tracker 上，同时打上 ready-for-agent 标签。动手写之前，它只会多确认一件事：你打算在哪些 seam 上写测试。所谓 seam，说白了就是系统里的接缝——测试从哪一层边界切进去最合适，提前说死，免得后面它写出一堆全是 mock 的水测试。

接着是 to-tickets。这里最关键的是纵向切片：每一张票都要端到端打通，能独立跑通验收，而且体量要控制在一个全新 context window 吃得下的范围内。它还会标清哪张票依赖哪张票，碰到大重构会自动按 expand、migrate、contract 的顺序排期；真正发出去之前，会先给你过一遍粒度，觉得切得太粗或太碎随时能调。

开工的话有两种节奏。想稳着点一张张盯，就用 implement：按约好的 seam 跑 tdd，写完跑 code-review，没问题就 commit。为了省时间，开发中途它只勤跑 typecheck 和单文件测试，全量测试留到最后跑一次，做完一张直接 /clear 换干净上下文。

要是你不想守在屏幕前一张一张点，直接上 implement-spec。它会把这批票当成任务图来调度，前置依赖一解开，就给每张就绪的票派一个全新的 implementer subagent，各开一个 worktree 并行干活，写完由 merger 合到同一条 integration branch 上，最后统一做 review。

这里的 code-review 设计也很有意思。它把检查拆成了两路并行：一路专盯代码规范加上 12 条 Fowler code smell，另一路专核对到底有没有按 issue 要求做全、有没有跑偏。分成两个 subagent 各自交报告，好处很实在——不会因为满屏命名和格式意见，把漏掉核心需求的硬伤给盖过去了。

这页右下角那两条经验，我觉得平时用任何 AI 编程工具都很受用。一个是别老想着靠在文档里写规矩让模型自觉遵守，凡是 lint、类型检查、pre-commit hook 或者 CI 能硬拦下来的错，直接上工具；就像底部引的那句原话，仓库不配 lint 从来都算不上“保持中立”，纯粹是白白放过了最省心的护栏。

另一条是给上下文减负。CLAUDE.md 和 AGENTS.md 每次开对话都会全量加载，越精简越好，放清楚路标就够了；至于编码规范，留给只看 diff 的 review agent 去把关，别在写代码上下文最紧张的时候一股脑全压上去。

/poteto-mode 是整套 pstack 的发动机。你把任务一丢过去，它先拿自己的话把目标复述一遍，也不等你点头，直接就开始干。

紧接着它会在 23 个 playbook 里挑最对口的那份，把里面的步骤原封不动拉进 todo。有个细节我特别认可：哪一步觉得用不上，它不会偷偷删掉，会在旁边写明跳过的理由。往下跑的时候，走到对应环节它会自动调别的 skill，比如动了跨函数边界的接口就先 /architect，有争议的方案上线前跑一遍 /interrogate，写的文案还会过一下 /unslop。最后验证完来汇报时，还会把哪条 principle 影响了哪个决定一并交代出来。

所以给它写 prompt 的习惯得跟着变一变。左边这五样里最关键的是验收标准——一定要能跑出明确结果，好让它自己验得出来。另外把你已经查到的线索、想看什么证据、以及红线约束也一并写清楚。

反过来，最容易踩的坑是管得太细。千万别在 prompt 里教它先干嘛后干嘛，也别一上来就把你猜的根因塞给它——playbook 本身已经把节奏排顺了，你手动指定 skill 顺序反而容易把流程搅乱。

你看右边文档里给的例子：先复现重复写入，有便宜的测试路径就用 /tdd，然后修完重跑。这里写 repro first 是在划约束，提一嘴 /tdd 是说明你想看测试证据，具体步骤还是让 playbook 自己掌舵。

接下来按干活的阶段，挑一批最值得单独拿出来用的 skill 聊聊。第一批是动手之前的摸底工具。

/how 用来搞清楚一段机制到底是怎么跑起来的。它会派一个只读 subagent 去翻代码，回来给你一份架构说明，标准是让一个刚接手这块代码的资深工程师看完就能干活。

/why 我个人特别喜欢，它的规矩非常硬：只从历史记录里找答案，绝不看着代码编理由。它会去翻引入这段代码的 commit 和 PR 讨论，直接引用作者当年的原话；如果是它自己推出来的，也会明明白白标出来。就算翻遍记录发现当年根本没人写过原因，它也会直说——至少让你知道这里有盲区，不至于看着别扭顺手一删，结果把线上搞炸了。

/blast-radius 专门治那种“看着就改了两行，但越看越不踏实”的 diff。它不会给你列一长串可能出事的清单吓唬你，直接揪出“这次改动不翻车最核心依赖的那个前提”，然后写个小脚本真跑一遍证明给你看。

下面还有两个日常很好用的：/teach 等于把 /how 和 /why 并行跑完合在一起，适合让它把一个复杂 PR、或者它自己刚做的改动给你讲透；/recall 就是周一早上的救星，翻翻你自己的聊天记录、git 和 PR 状态，帮你把上周干到哪、卡在哪、下一步干啥捞回来。

这几个都不改业务代码，哪怕你平时不开 /poteto-mode，单独拿来用也很值。开销上 /how 和 /why 最轻；/blast-radius 会真跑验证脚本，/recall 会并行派好几个 subagent，稍微重一点。

设计这几个招里，我觉得最出彩的是 /arena。平时用 AI 写代码大家都有体会，第一稿一不小心把架子搭歪了，后面全在围着烂设计打补丁。/arena 的思路很干脆：既然一次容易锁死在错的形状上，那就并行多出几版。

你看上面这套走法：先给所有候选发同一个 prompt，同时定好评分标准——不过评分标准藏着只给最后挑稿的看，候选自己看不到，免得应试作弊。接着它会在各自独立的 worktree 里并行跑 N 个候选，默认面板是三个不同模型各写一版。打分阶段特意换另一家厂商的模型来做 cross-judge，避免自己给自己打高分。把几份稿从头读完挑出底稿之后，最精华的是 Graft 这一步：把落选方案里最亮眼的设计手工嫁接到底稿上，最后跑一遍验证收尾。

/architect 搭在 /arena 上面，写法很符合一线工程师的直觉：先写调用方怎么用起来最顺手，再反推出类型和函数签名，函数体全留空，这份草图就是契约。默认情况下它定完草图不会停下来等你点头，直接往下写实现；你想把把关，在 prompt 里加一句 with checkpoint 就行。如果写着写着反复撞上同一种别扭，比如非得强转类型才能过编译，它会推倒草图重画，绝不硬凑。

最后一个 /interrogate 走的是对抗挑刺路线。几个模型轮番去攻你这次改动，规矩特别死：每条问题都必须拿真实运行结果说话，没跑过的一律不准往上写。这么一卡，那些虚头巴脑的代码风格吐槽全被过滤掉了，留下的全是能复现的硬伤。而且它只出报告，绝不擅自帮你改代码。

pstack 里大家讨论最多的用法大概就是过夜跑了：临睡前把任务交代清楚，第二天早上起来验收。

左上角是文档里的示范 prompt，作者管它叫“过夜合约”，里头塞了四样东西：要干啥、怎么算干完、给什么权限、真卡死了怎么收场。重点看标黄的那句：“完成的意思是零个旧调用方、所有 parser fixture 通过、旧 API 删干净。”这种跑个命令就能明确看出过没过的硬标准才管用；你要是写个“尽量迁一迁”或者“跑八个小时”，多半要翻车。最后一句留好退路——几个小时真推不动了，就停手把原因写下来，别在那儿白烧 token。

右边就是它夜里自己转的节奏：查一遍验收条件，做一笔有依据的小改动，跑真实产物验一下——真有推进就 commit，没用就直接扔，接着在 decisions.tsv 里补一行记录，然后进入下一轮，直到条件全过。这里有两条硬规矩：碰到瓶颈别干耗也别直接撂挑子，得换个思路试；更不能偷偷把验收标准放宽，硬宣布自己做完了。还要说明一点，prompt 里的 /loop 是 Cursor 内置命令，不在 pstack 里。

第二天早上回来，先敲 /ketchup，它会用大白话给你汇总一夜干了啥、有哪些卡着等你拍板；想细查过程，再跑 /show-me-your-work 逐行翻决策账本，直奔 Attention 那一段就行。

不过真想试之前，先对照左下角那四个前提。作者说得很直白：这件事你自己得先干过或者盯着 agent 跑通过一次，知道好结果长什么样；得给它配齐工具和反馈信号，让每一步都能自己验出对错；而且你得提前翻过几份 transcript，把那些老掉进去的坑做成检查脚本。这些都没准备好就撒手跑一整夜，大概率早上起来收获一串没法合的 commit。

pstackdocs/guide/09-make-it-yours.md

任务做完了，怎么别让同样的坑下次接着踩？pstack 给了三个事后复盘的命令，差别就在于教训最后改在什么地方。

/reflect 改的是 skill。它会派三个 reviewer 同时翻你这次的会话记录，分别从判断、工具使用和发散思路三个视角挑毛病，再交给一个 synthesizer 汇总成采纳、拒绝和待办三栏。改动 skill 影响面大，往后每次跑任务都会跟着变，所以它每一条都得等你逐行批准才动手。它还定了一条很清醒的规矩：只发生过一次的意外不算教训，别动不动往 skill 里塞补丁。

中间的 /correct 改的是代码仓库本身，这个思路很对工程胃口。它专盯 agent 在这个项目里一犯再犯的同类错——至少出现两次才算数——然后按优先级从高往低堵漏洞。最好能改架构，让这种错根本写不出来；退一步靠类型、lint、CI 直接拦死；再不行补行为测试；文档和规则排在最末位。为啥？因为代码和检查挂了会直接红，agent 漏看一段文档的时候，什么警报都不会响。

右边的 /automate-me 则是整理你自己的工作习惯，从最近会话里把你的偏好捞出来，生成一套你个人名字的 mode skill，互动也很克制，一次就问一两个多选题。回头对照一下第一章的 /retro：/retro 只给建议不动手，/reflect 改 skill，/correct 改仓库，三个各管一摊，等讲到跨仓库组合时再看怎么把它们串起来。

除了 playbook 和功能型 skill，pstack 还有 24 条很短的 principle，按主题分成核心、架构、验证、委派和元原则五块。

这一屏肯定不一条条念。我想聊的是它们用起来有多省事：你不用敲斜杠命令去调用，直接在对话里喊名字就行。比如 agent 兴冲冲地说测试过了，你觉得不踏实，回一句 “apply prove it works, show me the real output”，它立马明白你在要什么——因为它开干前已经扫过索引、读过那条规则了。喊个名字就能把一整段要求调出来，省得每次从头解释一遍。

pstack 的 Prototype playbook 思路完全不一样，连斜杠命令都没给，你在 /poteto-mode 里提一句 prototype 就会触发。它的核心目的是尽量少打断你——只要是试跑一下就能见分晓的技术分叉，agent 自己钻进隔离的 scratch 目录里搭最小脚本，或者做个带切换器的页面截好图，把结果、耗时、利弊和推荐方案一起摆到你面前。你点完头，后面的活直接交给 Feature playbook 去干，scratch 里的临时代码跟生产代码井水不犯河水。

组合用法 · 建议，非作者文档配方 1

理清对照之后，后面几页给几套能照着试的搭配。先看第一套，把 Matt 的主流程跟 plannotator 接在一起。

这套适合做一个中等大小的 feature。你用 /grill-with-docs 把需求问清楚、/to-spec 也把文档写出来了，但真要拆成一堆 ticket 开工之前，你心里可能还想踏实一点——最好自己逐段把这份 spec 过一遍，或者甩给同事看看，确认没漏什么再往下拆。

插进去的那一步很简单，就在 /to-spec 和 /to-tickets 中间，手动跑一下 /plannotator-annotate，指到 spec 文件并带上 --gate。浏览器弹出来之后，哪儿觉得不对劲直接划出来批注，发回去让 agent 改，直到你点下批准，才继续往后拆票、写代码。

有人可能会问，plannotator 不是会自动拦截吗，干嘛还要手动敲这一步？因为 /to-spec 是直接把 spec 写到 issue tracker 里的，全程压根没进过 plan mode，所以默认的自动拦截钩子不会被触发。

真要跑这套流程，有三个小细节提前留意下。跑 /setup-matt-pocock-skills 初始化的时候，tracker 要选本地 markdown，不然 spec 发去外部平台了，本地 .scratch 目录下根本拿不到文件。另外，Matt 那边要求聊需求、写 spec、拆 ticket 这几步留在同一个 context window 里，中间插了批注也千万别敲 /clear，免得上下文断掉。最后就是命令参数别漏了 --gate，不带的话打开的只是普通批注界面，没有那个批准放行的按钮。

接着上重一点的，跑 pstack 的 /interrogate。它会拉出好几个专门唱反调的视角去攻你这条分支，而且硬要求每报一个问题都得附上跑出来的失败输出，不许空口猜。中间那段英文是 pstack 文档里的原话，大意是带着怀疑审整条分支，除非是真 bug 或者回归，别扯无关痛痒的小毛病。
