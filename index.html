Agent Skills 分享概念

开始之前先对齐一个概念，后面会反复用到。skill 有两种触发方式。

第一种是 user-invoked，只有你自己敲斜杠命令才会跑。这类 skill 负责编排，决定整个流程怎么走。第二种是 model-invoked，你可以敲，agent 也会在它觉得任务匹配的时候自己加载，这类 skill 装的是可复用的纪律。

pstack 不太一样，它几乎所有 skill 都只能手动触发，所以装了 pstack 之后什么都不会自动发生，你得敲命令，或者交给 poteto-mode 去路由。

这套 skill 是为了修四个失败模式而写的，README 里列得很清楚。先解释三个待会儿会出现的词。ADR 是架构决策记录，一小段文字记下一个决定和它的理由。红绿循环是先写一个失败的测试，再写代码让它通过。“加深”模块，是让模块接口小、里面藏的东西多；巡检找的就是接口大却没干多少事的浅模块。

第一个最常见：agent 没做出你想要的东西。解法是 grilling，让 agent 在动手前反过来盘问你。Matt 说这是他最受欢迎的 skill，建议每次要改东西都用。

第二个：agent 太啰嗦。原因是它不懂你项目里的行话。解法是建立一份共享词汇表，这件事内置在 grill-with-docs 里。

第三个：代码不工作。解法是反馈回路，对应 tdd 和 diagnosing-bugs。

第四个：agent 写得太快，代码库很快变成泥球。解法是关心代码设计，对应 improve-codebase-architecture，他建议每隔几天跑一次。他自己也说了，这是巡检，不是救火，真正的烂摊子它不会替你理清。

Design tree

每个决定会分叉出依赖它的后续决定。

一轮问完整个 frontier

前置条件已定、现在就能问的问题，一次全问。依赖本轮答案的留到下一轮。

每题带推荐答案

措辞保证你回 “yes” 就等于接受推荐。你只需要纠正不同意的。

事实它查，决定你做

能从代码里查到的不问你，派 sub-agent 去查，并且不阻塞其它问题。

结束条件

frontier 为空，并且你确认已达成共识之前，它不动手。

mattpocock/skills“Finding facts is your job, never the user's.”

grilling 具体是怎么问的。左边是一段示意对话。

它把要讨论的事情看成一棵决策树，每个决定会分叉出依赖它的后续决定。它按轮提问，每一轮把现在就能问的问题一次性全问出来，这批问题叫 frontier。

每个问题都有编号，并且带着它自己的推荐答案。措辞是有讲究的：保证你回一个 yes 就等于接受它的推荐。所以实际用起来很省力，大部分问题你回 yes，只在不同意的地方多说两句。

你回答之后，树的形状变了，新的问题被解锁，它重新计算 frontier 再问下一轮。比如这里我说要导出全部数据并且走后台任务，它下一轮就会问任务完成怎么通知。

还有一条分工原则我很喜欢：事实归 agent，决定归你。能从代码里查到的东西它不会问你，会派一个 sub-agent 去查。最后，在你明确确认已经达成共识之前，它不会开始动手。

/grill-with-docs 留下什么

一份词汇表，和少量 ADR

GLOSSARY.md（结构示意） # Course Video Manager 一两句话说明这个 context ## Language **Materialization cascade**: A lesson inside a section being given a real place on the file system. _Avoid_: "made real", "written out"

规则

只收本项目特有的概念；定义它是什么，不写实现细节；一个概念只留一个词，其它列进 Avoid。文件在第一个术语定下来时才创建。

README 里的前后对比

之前：“There's a problem when a lesson inside a section of a course is made 'real' (i.e. given a spot in the file system)”

之后：“There's a problem with the materialization cascade”

ADR：三个条件同时满足才提议写

  • 难以回退
  • 没有上下文会让人意外
  • 确实做过取舍

位置 docs/adr/0001-slug.md，一段话就可以是一篇 ADR。

词汇表的好处不止省字：命名一致，代码更好找，agent 思考时花的 token 也更少。
mattpocock/skillsdomain-modeling · GLOSSARY-FORMAT.md · ADR-FORMAT.md

grill-with-docs 会留下两样东西。第一样是 GLOSSARY.md，项目的词汇表。格式很轻：一个标题，一段说明，然后每个术语一个加粗的名字、一两句定义，再列出应该避免的同义词。左边这段是结构示意。

README 里有个例子很能说明问题。没有词汇表的时候，agent 会说“当课程某个小节里的一节课被变成真实的，也就是在文件系统里有了位置的时候，会出问题”。有了词汇表，它只说“materialization cascade 有问题”。一句话变成一个词，这种节省每个 session 都在发生。

最要紧的规则有三条：只收本项目特有的概念，通用的编程概念不收；只写它是什么，不写实现细节；一个概念只留一个词。

第二样是 ADR。它很克制，三个条件同时满足才会提议写：难以回退、没有上下文会让人意外、确实做过取舍。而且 ADR 可以只有一段话。

Matt 在 README 里说，这可能是整个仓库里最酷的技巧，我同意。

它里面还有一棵很实用的决策树，回答一个大家天天遇到的问题：一个阶段结束了，上下文怎么办。从上往下问五个问题，第一个回答“是”的胜出。能继续就继续；上下文跟后面无关就 clear；要换工具、换目录、交给别人就 handoff；剩下的活能无人值守完成就开 subagent；都不是，才 compact。

这里有个概念叫 smart zone，大约 15 万 token 以内模型推理还很敏锐，快到这个线的时候就该在阶段边界处理上下文了。

还有一个它文档里自己承认的坑：agent 有时会说一半的 skill 没装。那是因为手动触发的 skill 不出现在 agent 能看到的列表里。其实都装了，直接敲命令就行。

两种调用方式

带一个松散的想法 → 画地图：定目的地、摸清前沿、建 map 和 ticket、并行跑 research，然后停。

带一张已有的 map → 解一张 ticket：认领、解决、写结论、关闭、更新地图。

wayfinder 是给特别大的工作用的：一个全新的项目，或者一个巨型 feature，大到一个 agent session 装不下，而且从这里到终点的路你现在看不清。

它的做法是在 issue tracker 上建一张地图。地图是一个 issue，有五个小节：目的地、备注、已做的决定、还没说清的部分、范围之外。地图下面挂着一批子 issue，每个子 issue 里只有一个问题，这些叫 decision ticket。

ticket 有四种类型。research 是让 subagent 去查一手资料，可以无人值守；prototype 是做个能跑的东西来回答；grilling 是默认类型，就是追问；task 是决策之前必须先做的手工活，比如开通账号。

调用有两种方式。带一个松散的想法调用，它画地图，然后停。带一张已有的地图调用，它解决一张 ticket。规则是每个 session 最多解一张，这样每个决定都是在干净的上下文里做的。

两点提醒。第一，它产出的是决定，不是交付物，地图清晰之后要交给 to-spec。第二，不要滥用，ask-matt 自己说它更慢更重，范围清晰的 feature 绝对不要用它。

retro，复盘。它和我们平时理解的复盘有一点不同：它复盘的对象是 agent 的运行环境，不是代码本身。

它背后有两个判断我觉得很值得带走。第一，机械性的错误一律做成确定性的检查，不要写成规则指望 agent 遵守。第二，编码规范应该由 review 的 agent 来执行，因为写代码的那个 agent 上下文压力最大。

prompt 里要写的五样

  • 目标
  • 完成标准：必须能判定通过或失败
  • 你想看到的证据
  • 你已经知道的
  • 真实的约束：“repro first”、“先别改代码”、“让我 review 再继续”

一条真实的示例 prompt

/poteto-mode repro the duplicate write first. if there's a cheap test path, /tdd it. then fix and rerun.

自主程度

可逆的操作直接做。不可逆的写操作（force-push 共享分支、deploy、删数据、给客户发消息）必须停下来问。

什么时候不用它

小而明显的修改不需要。它的 subagent 和评审面板要花真实的 token。

pstack“Never hand the human a check you could run.”

poteto-mode 是整个 pstack 的核心。它被调用之后做这么几件事。

先用自己的话复述你的目标，而且不等你确认就往下走。然后从 23 个 playbook 里匹配一个，把 playbook 的步骤原样抄进 todo 列表，跳过的步骤不会删掉，而是标上跳过的原因。接着按步骤执行，步骤触发的时候路由到其它 skill，比如跨函数边界的改动先 architect，有争议的设计上线前 interrogate，写文字过一遍 unslop。最后验证并汇报，汇报里要点名哪条原则影响了哪个决定。

所以给它写 prompt 的方式和平时不一样。要写五样东西：目标，完成标准，你想看到的证据，你已经知道的信息，以及真实的约束。完成标准最关键，它必须是能判定通过或失败的。

不要写的东西同样重要：不要写怎么做，不要列 skill 的顺序，一开始也不要写你对原因的猜测。playbook 已经把顺序排好了，你手写一遍反而会打乱它。

右边是文档里的一条示例：先复现重复写入，有便宜的测试路径就先写测试，然后修复并重跑。注意这里的 repro first 是约束，不是做法；点名 tdd 是告诉它我想要哪种证据，不是替它排顺序。另外两件事：可逆的操作它直接做，force-push、deploy、删数据这类它会停下来问；改一行文案这种小而明显的修改不要用它，它派出去的 subagent 和多模型评审是真花 token 的。

它的座右铭是：永远不要把一个你自己能跑的检查交给人。

接下来按工作阶段过一遍那些可以单独调用的 skill。第一个阶段是理解，也就是动手之前。

how 回答“它是怎么工作的”。它派一个只读的 subagent 去探索代码，给你一份架构解释，标准是让一个不熟悉这块的资深工程师读完就能开始干活。

why 回答“为什么是这样”。它的规则只有一条：从记录里回答，不从代码里猜。它会去读引入这段代码的 commit 和 PR 讨论，引用作者当时的原话，把自己的推断明确标成推断。如果记录里没写，它会告诉你没人写下原因，这本身也是一个答案。这个 skill 能防止“看不懂就删掉”。

blast-radius 回答“它会弄坏别处什么”。它不给你一长串可能性，而是找出这次改动之所以安全所依赖的那一个事实，然后真的跑代码去证明它。

这几个 skill 都不改你的业务代码，单独拿出来用也很值。其中 how 和 why 最轻；blast-radius 会写一个小脚本并真的跑一遍，recall 会并行派出多个 subagent。

第二个阶段是设计。pstack 的指南里有一张很实用的阶梯，回答的问题是：一个任务值得花多少设计力气。

设计阶段最有特色的是 arena。它的想法是：一次尝试容易把东西锁死在错误的形状上，那就多做几版。

六个阶段。Frame：所有候选拿到同一个 prompt，同时定好评分标准，但评分标准只给最后挑选的人看，候选自己看不到。Fan out：N 个候选并行，各自在独立的 worktree 里做。Cross-judge：找一个不同厂商的模型来打分，避免自己评自己。Pick：把每一份从头读到尾，挑一份做底稿。Graft：这一步是精华，把落选方案里最强的部分手工嫁接到底稿上。最后 Verify。

architect 在 arena 之上。它的特点是先写调用方怎么用这个东西，再从用法推出类型和函数签名，函数体先留空。这份草图就是契约。默认它不会停下来等你确认，直接进入实现。如果实现的时候反复撞到同一种别扭，比如类型非得强转才能编译，它会丢掉草图重新设计。你想让它停下来给你看，就加一句 with checkpoint。

interrogate 是对抗式 review。多个模型扮演对手去攻击一次改动，规则很硬：每个发现都必须用真实的运行来证明，没跑过的不许报。所以它不会给你风格意见，只给你能复现的问题。它也只报告，不修。

pstack 很受关注的一个用法是过夜跑：睡觉前交代任务，早上起来审计。

左上是指南里的示例 prompt，它管这个叫过夜合约，包含四样东西：目标，完成条件，权限，退路。看黄色这句：完成的意思是旧的调用方为零，所有 fixture 通过，旧 API 被删除。这是一个能判定真假的谓词，不是“尽量迁移”，也不是“跑八个小时”。最后一句是退路：真卡住了就停下来，写明原因。

右边是它的循环：检查完成条件，做一个有证据支持的最小改动，对真实产物验证，有进展就提交，没帮助就丢弃，然后在决策日志里记一行。一直循环到完成条件为真。它有两条纪律：进入平台期不是停下的理由，要换思路；绝不放宽完成条件来宣布胜利。

pstackdocs/guide/09-make-it-yours.md

最后一个阶段是事后，把教训留下来。pstack 有三个命令，区别在于教训落在哪里。

reflect 把教训落到 skill 上。它派三个 reviewer 并行读这次会话，分别从判断、工具、发散三个角度找教训，再由一个 synthesizer 筛成三栏：采纳、拒绝、待办。重点是，每一条都要你逐行批准才会真的去改 skill，因为改 skill 会影响以后每一个 agent。它还有一句话：一次性的事不算教训。

correct 把教训落到仓库上。它找的是 agent 在这个仓库里反复犯的错误类别，同一类出现两次才算数。然后在尽可能高的层级修掉。最高层是架构，让这种错误根本写不出来；其次是类型、lint、CI，让它过不了；再其次是测试；最后才是文档和规则。为什么文档放最后？因为 agent 跳过文档的时候，什么都不会报错。

automate-me 把教训落到你个人身上。它从你最近的会话记录里挖出你反复出现的工作偏好，生成一个你自己名字的 mode skill。

这里可以和上一章的 retro 对一下。retro 只给建议，不动手。reflect 改 skill，correct 改仓库。三者不冲突，后面组合的部分会把它们串起来。
